# spfi_encrypt on the AMD VCK190

Board target of the system [spfi_encrypt](../../README.md) for the AMD VCK190 evaluation board (XCVC1902-VSVA2197).
The SpaceFibre port of the system uses the QSFP1 cage with four lanes at 6.25 Gbit/s. The board top level
`spfi_encrypt_vck190_top` adds what the board needs around the generated system: the CIPS with the system clock and
the fabric reset, the buffer of the transceiver reference clock and two LEDs.

| --- | --- |
| [src/spfi_encrypt_vck190_top.vhd](src/spfi_encrypt_vck190_top.vhd) | Board top level |

## Clocks and reset

| Clock | Frequency | Source | Use |
| --- | --- | --- | --- |
| `clk_pl_0` | 200 MHz | PMC clock generator of the CIPS (`pl0_ref_clk`) | `Clk_sys` of the system; free-running clock of the transceivers |
| `gt_refclk` | 156.25 MHz | Clock generator 8A34001 (U219), output Q1, to MGTREFCLK1 of GTY quad 200 | Reference clock of the transceivers (`pa0_RefClk` through IBUFDS_GTE5) |
| lane clock | 156.25 MHz | Transmit clock of the transceivers (BUFG_GT in `ofb_pa_gty`) | Core and lane clock of the SpaceFibre port, generated inside the system |

The output Q1 of the 8A34001 does not run at 156.25 MHz by default: program it with the clock tool of the board's
system controller (Board Evaluation and Management Tool or the system controller command line, see the VCK190 user
guide UG1366) before the device is configured.

The fabric reset `pl0_resetn` of the CIPS resets the system. An `olo_base_reset_gen` (triplicated synchronisers,
1000 cycles) releases it synchronously to the system clock. This generator is provisional: the transceiver adapter of
the system evaluates its reset in the free-running clock domain without a synchroniser of its own; once the adapter
synchronises its reset itself, the fabric reset drives `Rst` of the system directly.

## Pins

| Signal | Pins | Function |
| --- | --- | --- |
| `GtRefClk_P`, `GtRefClk_N` | AD11, AD10 | MGTREFCLK1 of GTY quad 200 |
| `Qsfp_TxP(i)`, `Qsfp_TxN(i)` | lane 0: AF7, AF6; 1: AE9, AE8; 2: AD7, AD6; 3: AC9, AC8 | QSFP1 transmit, channel i of quad 200 (GTY_QUAD_X1Y0) |
| `Qsfp_RxP(i)`, `Qsfp_RxN(i)` | lane 0: AF2, AF1; 1: AE4, AE3; 2: AD2, AD1; 3: AC4, AC3 | QSFP1 receive |
| `Led(0)` | H34 (GPIO_LED_0) | Toggles every 2^27 cycles of the system clock (about 0.7 s): the device is configured and the clock runs |
| `Led(1)` | J33 (GPIO_LED_1) | On when the reset of the system is released |

Lane i of the system is channel i of the quad and must be connected to lane i of the far end; the SpaceFibre port
does not compensate swapped lanes. It detects inverted receive polarity per lane itself during the lane
initialisation.

## Constraints

- `constr/spfi_encrypt_vck190.xdc`: pins, location of the quad, reference clock.
- `systems/spfi_encrypt/hdl/spfi_encrypt.xdc`, generated by the Composer and scoped to the entity `spfi_encrypt`:
  the asynchronous reset input and the crossings between the system clock and the lane clock (5 ns, the period of the
  faster clock).
- The scoped constraints of the clock crossings of Open Logic, area base (`olo_base_constraints_amd.tcl`). The
  scoped constraints of `olo_intf_sync` are not loaded: they constrain device pins, and the system uses
  `olo_intf_sync` for internal asynchronous signals only, which the clock pair constraints cover.

## Build

The build needs AMD Vivado 2025.2 with device support and a synthesis licence for the XCVC1902, the submodules in
`cores/` and the generated top level in `systems/spfi_encrypt/hdl/`. A build computer without network access gets the
repository as Git bundles (`tools/make_offline_bundle.py`, [hardware test procedure](docs/hardware_test.md),
section 3).

```shell
vivado -mode batch -source systems/spfi_encrypt/targets/vck190/tcl/build.tcl [-tclargs <step>]
```

| Step | What the script does |
| --- | --- |
| `project` | Creates the project: the sources of the compile order exported by the Composer, the transceiver wizard instance of OpenFibre (`ofb_gtw`, 156.25 MHz reference clock), the CIPS block design (`vck190_cips`, JTAG boot), the board top level and the constraints |
| `rtl` | `project` and the RTL elaboration of the design |
| `synth` | `project` and synthesis |
| `impl` | Synthesis, implementation and the reports in `results/` |
| `all` (default) | Synthesis, implementation, device image and the reports in `results/` |

The project is `vivado_out/spfi_encrypt_vck190` in the repository, or the directory in the environment variable
`RS_VIVADO_OUT`. On Windows the project path must not be longer than about 40 characters: the device image step
compiles the platform loader firmware in a deep directory below the project, and with a longer path
`write_device_image` fails; use a short directory, for example `RS_VIVADO_OUT=C:/rs`.

`results/` in the project directory holds the device image, the timing summary, the utilisation (flat and per
block), the methodology and DRC reports and `build_info.txt` with the Vivado version and the commits of the
repository and of its submodules. Section 4 of the [hardware test procedure](docs/hardware_test.md) lists the
expected results and messages.
